HOW I WORK · AGENTIC ENGINEERING

Executed checks over skimmed diffs.

I use Claude Code as the main driver and push work to subagents to keep its context clean. I delegate some subtasks to other models (OpenAI models and open-source ones such as Kimi and Qwen) when a second opinion or a cheaper model fits. The agent does most of the typing; I own the decisions and the verification, which is how I ship several PRs a day.

  • STAGE 01
    SCOPE
    Usable increments, with a written "not now"

    I split each project into increments, Kniberg's skateboard-to-car. On my current legal-services project, the launch is increment 1: buying a contract, and nothing else. Everything beyond it is a written "not now", so agents don't build toward it.

    Skateboard to carExplicit non-goals
  • STAGE 02
    SPEC
    Spec, plan, tasks, then build

    Each slice goes through spec-kit, with slash commands running every step in a subagent that returns a short report. Business, legal, and one-way architecture calls go in a decision log that agents must check before planning. A read-only "drift" agent compares a branch against the client's documents and the log, and a "skeptic" agent argues against building a feature now (build, shrink, defer, or cut). Before any UI exists, I generate HTML canvases and diagrams to see what will be built.

    spec-kitDecision logDrift agentSkeptic agentHTML canvases
  • STAGE 03
    VERIFY
    Tests first, and a Definition of Done

    TDD by default: the agent writes a failing test first, usually an integration test, then the smallest change that passes. Bug fixes get a regression test. A written Definition of Done covers tests, typecheck, lint on the touched code, and authorization and failure paths. The completion report separates Verified (checks actually run) from Uncertain, so I know where to look.

    TDDIntegration testsVerified vs Uncertain
  • STAGE 04
    SHIP
    Small PRs, bounded blast radius

    One Git worktree per PR, so my main checkout is never edited and parallel agents don't collide. One user story per slice keeps each diff reviewable. Subagent code review runs against the task's scope only, with a cap on findings; CI plus three review checks run on every PR and the agent fixes what matters. Before merging I review before/after screenshots with red arrows on what changed, or a narrated video of the end-to-end run, and check it did what I intended.

    Git worktreesCIScoped reviewVisual reviewPlaywright
  • STAGE 05
    GUARD
    Hard guardrails, and reading where it counts

    Permissions and hooks stop the agent from touching secrets, committing, pushing, installing packages, or making network calls without my approval. A privacy-law review skill runs on anything touching personal data. I read code selectively, on the risky paths: auth, payments, and personal data.

    Permissions & hooksPrivacy review skillSelective code review
CLIENT · WEB · IN PROGRESS · PRE-LAUNCH

Legal contracts you can buy online, built for the Dominican Republic.

Papeles Legales is a legal-services startup. Today, getting a contract (a rental, a loan, a vehicle sale) in the Dominican Republic means finding a lawyer. The first release lets a stranger pick a template, answer a questionnaire without an account, pay by card, and download the finished PDF with its invoice.

It is not live yet: the purchase flow works end to end in test mode, and the local card gateway (Azul), electronic invoicing, and the production environment are still being finished. I'm building it as the sole engineer, scoped as a deliberately small first increment and built with an agent-driven workflow of specs, tests, and a decision log (see "How I work" under Capabilities).

  • STAGE 01
    BUY
    Questionnaire to PDF, no account

    Five contract templates, each party a person or a company. Customers edit only their answers, never the contract text. The document is generated from a Word template with fixed pagination, unsplit signature blocks, and a watermarked preview on demand before paying. Registration happens at the review step.

    ReactClerkdocxtemplaterTemplate engine
  • STAGE 02
    PAY
    Payments and electronic invoicing

    One payment per order, checkout expiry, and webhook-confirmed fulfillment, running on Stripe in test mode behind a payment-provider interface so the Dominican bank gateway (Azul) can replace it. Every paid order also gets an electronic invoice (e-CF) for the DGII, built against a fake provider until the real one is chosen. Background jobs expire unfinished checkouts and issue the invoices.

    Stripe (test mode)Azule-CF / DGIIpg-boss jobs
  • STAGE 03
    OPERATE
    Staff workspace and audit trail

    The team loads and edits contract templates through a questionnaire builder, with a second person's approval required before a version is published. Role-based access separates operations, support, and content staff, and an audit log records who did what, from which IP and browser.

    Role-based accessVersioned templatesAudit log
  • STAGE 04
    SHIP
    Google Cloud, proof of concept first

    The infrastructure is defined in Terraform: a VM running Docker Compose, Cloud SQL for PostgreSQL, private storage buckets with a 10-year retention policy, and secrets in Secret Manager. A database restore has been drilled on the proof-of-concept deploy; production, daily backups, and the final end-to-end run are still open. A Playwright golden-path test covers the purchase flow end to end.

    Node.jsExpressPostgreSQLPrismaTerraformGoogle CloudPlaywright

CASE STUDY · SOLE ENGINEER · IN PRODUCTION · CLIENT CONFIDENTIAL

From raw satellite signal to centimeter-level answers, daily and unattended.

Some monitoring problems need to know whether a point on the ground moved by centimeters. That demands raw GNSS observation data, careful post-processing, and infrastructure that ingests, computes, archives, and alerts without manual babysitting.

I designed, built, and operate that platform end to end for a client. Specifics are kept general here; happy to go deeper in conversation.

  • STAGE 01
    ACQUIRE
    Field acquisition

    Dual-band GNSS receivers capture raw multi-constellation observations at remote sites. Cellular uplinks move the data out, designed for locations with no fixed connectivity and intermittent power.

    Dual-band GNSSRaw observation dataCellular uplink
  • STAGE 02
    INGEST
    Ingestion & storage

    A Node.js ingestion layer receives daily observation files, validates them, and archives raw data structured for reprocessing: raw signal is never thrown away, so the whole history can be recomputed when processing improves.

    Node.jsTypeScriptCloud object storage
  • STAGE 03
    COMPUTE
    RTK post-processing

    Containerized open-source RTK workloads run on serverless container compute, resolving carrier-phase ambiguities against reference station data to produce centimeter-level position solutions. Compute scales with the job and costs nothing when idle.

    Open-source RTKDockerServerless containers (AWS)
  • STAGE 04
    WATCH
    Monitoring & alerting

    Automated checks verify that every site delivered its expected daily data and raise an email alert the moment a receiver goes quiet. A silent sensor surfaces within hours, not weeks.

    Automated checksEmail alerting

A homelab run like production, because it does production work.

Three Raspberry Pis (models 3, 4, and 5) and a Mac mini meshed into a private network with Tailscale, each running services organized for clean operations. It's a learning ground for distributed systems, but it also carries real responsibilities.

  • LAYER 01
    NETWORK
    Private mesh

    Tailscale connects every node into a zero-config WireGuard mesh, with HTTPS serving for select services. No exposed ports, no dynamic-DNS fragility, access from anywhere.

    TailscaleWireGuardHTTPS serve
  • LAYER 02
    SERVICES
    Self-hosted apps

    Docker Compose stacks for personal cloud storage and sync, PDF tooling, and workflow automation. Each service lives in its own directory convention with isolated volumes, easy to rebuild, easy to reason about.

    Docker ComposeNextcloudStirling-PDFn8n
  • LAYER 03
    AUTOMATION
    Workflow automation

    n8n runs scheduled and event-driven workflows for personal automation: integrations, notifications, and recurring chores that would otherwise need a human. If I do something twice by hand, it becomes a workflow.

    n8n workflowsScheduled jobsNotifications
  • LAYER 04
    PRIVACY
    Document anonymization pipeline

    Send a PDF or photo to a private Telegram bot and get back text with personal data replaced by markers like <PERSON>, safe to hand to an LLM. n8n orchestrates OCR through Stirling-PDF and detection through Microsoft Presidio, extended with custom recognizers for Dominican IDs and a personal dictionary. It's built to fail closed: if a known term or a valid ID number survives redaction, or anything else goes wrong, it stops and says so instead of guessing. Backed by a 229-case test suite, an allow-list of Telegram users, and execution logging switched off so documents are never stored.

    n8nMicrosoft PresidioStirling-PDF OCRTelegram botFail-closed

    LOCAL AI
    Private inference node

    A Mac mini (M6, 32 GB) serves open-weight MLX models through Ollama, reachable only over the Tailscale mesh. n8n workflows call it for summarizing and classifying, it stands in as the AI backend while I build apps, and it's where I benchmark new models against real tasks. Nothing leaves the network.
